## Visual Hierarchy

**Focal point declaration:** on the Tarefas page header, the primary visual anchor is the **"+ Nova
Tarefa" button** (green, top-right of the header row — the one CTA the eye should land on first).
Within every row/card in Lista/Kanban/Gantt, the primary visual anchor is the **status pill (icon +
color + label)** — it is what tells the user, at a glance, what state each task/subtask is in, ahead
of title, dates, or assignee. Everything else (task ID, dates, assignee chip, hierarchy captions) is
secondary and rendered smaller/muted relative to those two anchors, consistent with the Typography
and Color contracts above.

## Spacing Scale

The project does **not** run a strict 8-pt scale — it uses Tailwind's default spacing scale
including half-steps (`1.5`, `2.5`), which is the established compact-density convention for this
dense B2B table/kanban/gantt app. Declaring the *real* values in use rather than inventing a fresh
8-pt scale:

| Token | Value | Usage |
|-------|-------|-------|
| 2xs | 4px (`gap-1`) | Icon-to-text micro gaps (badge glyph + label) |
| xs | 6px (`gap-1.5` / `py-1.5` / `px-1.5`) | **Default** dense row/badge/button padding — table cells, pills, small buttons |
| sm | 8px (`gap-2` / `px-2` / `py-2`) | Standard compact spacing — card padding, column gaps |
| sm+ | 10px (`px-2.5`) | Input/button horizontal padding |
| md | 12px (`gap-3` / `px-3` / `py-3`) | Card body padding, Kanban board gaps between columns |
| lg | 16px (`px-4` / `py-4`) | Dialog body padding, page section padding |
| xl | 20px (`px-5`) | Dialog header/body padding (mirrors `RiskFormDialog`) |
| 2xl | 24px (`px-6`) | Page-level horizontal padding (`/tarefas` page wrapper, mirrors `/opportunities/[id]/page.tsx`) |

Exceptions:
- Half-steps (6px/10px) are the norm here, not an exception — do not "round" them to a stricter
  8-pt scale when implementing.
- No 44px touch-target rule. This is a desktop-first, mouse/pointer-first dense UI (`PointerSensor`
  with a 5px activation distance is the only touch-adjacent precedent). Minimum interactive hit
  area for icon-only buttons (expand/collapse chevron, edit/delete icon buttons) is **28px**
  (`w-7 h-7`), matching `DeleteRiskButton`'s close button and the existing risk-table action icons.
  Do not introduce 44px targets — it would be visually inconsistent with every other icon button in
  the app.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label (uppercase column headers, form field labels, badges) | 10px | bold (700) | 1.2 |
| Body (table cells, form input values, plain copy, blocked-reason text) | 12px | regular (400) | 1.5 |
| Heading (dialog titles, Tarefas page title, column headers) | 14px | bold (700) | 1.2 |
| Emphasis (task IDs, buttons, status pill text, card titles) | 11px | semibold (600) | 1.4 |

**3 weights** used across new components: **bold (700)** for labels/headings/IDs, **regular
(400)** for body copy, and **semibold (600)** reserved specifically for interactive emphasis
(buttons, pills, card titles). This is a deliberate exception to a stricter 2-weight rule, kept
because it matches the live app's established convention exactly — the same justification pattern
as the Spacing section's half-step exception. Verified directly against production code: `bold` +
`semibold` are both real, distinct weights on the same component family this phase extends
(`components/opportunities/kanban/Card.tsx:61` card title `font-semibold` vs. `:66` FTE badge
`font-bold`; `components/opportunities/modal/risk/RiskForm.tsx:281` Cancelar `font-semibold` vs.
`:288` Salvar `font-bold`), alongside the unweighted **regular (400)** body
copy inherited from `body{}` in `app/globals.css` wherever no `font-*` class is applied (form
textarea values, blocked-reason text). Do not introduce `font-extrabold`/`font-medium` in this
phase's new components — those are reserved elsewhere (score numbers, KPI displays) and are out of
scope here; the 3-weight set above (bold/semibold/regular) is the full, closed set for Phase 16.

"Display" role from the generic template is **not used** in this phase — Lista/Kanban/Gantt are
dense data views, not marketing/KPI surfaces. No component in this phase needs a size above 14px.

### Task status palette (new — `TASK_STATUS_META`, mirrors `lib/opportunities/status.ts` shape)

Every status is rendered as **icon + label + color**, never color alone (accessibility
requirement — see UI Considerations). Reuse the exact same semantic vocabulary already
established for opportunity statuses where the meaning overlaps (Backlog):

| status (DB) | Label (pt-BR) | Icon | color | bg |
|---|---|---|---|---|
| `backlog` | Backlog | ⏳ | `#f59e0b` | `#fef3c7` |
| `em_andamento` | Em Andamento | 🔄 | `#3b82f6` | `#dbeafe` |

## Phase-Specific View & Interaction Contract

> Extends the generic template with the concrete component/route contract this phase's 3 views
> and forms need. Executor implements against this section directly; it is not exploratory.

### Routes

| Route | Purpose |
|-------|---------|
| `/opportunities/[id]/tarefas` | Fullscreen sub-route (Server Component), single fetch, hosts Lista/Kanban/Gantt. Header: **"← Voltar à oportunidade"** + page title **"🗂️ Plano de Atividades"** + view switcher + "+ Nova Tarefa". |
| `/opportunities/[id]/tarefas?view=lista\|kanban\|gantt` | View selection — default `lista` when param absent/invalid (mirrors `parseView` in `toolbar.tsx`, same fallback-safe pattern). |
| `/opportunities/[id]/tarefas?tarefa=new` | Soft-path: `TaskFormDialog` overlay (create root task) stacked over the fullscreen page, `z-[60]`, mirrors `RiskFormDialog` exactly. |
| `/opportunities/[id]/tarefas?tarefa=new&parent=<taskId>` | Soft-path: create subtask of `<taskId>`. |
| `/opportunities/[id]/tarefas?tarefa=<taskId>` | Soft-path: edit dialog for `<taskId>` (root or subtask). |
| `/opportunities/[id]/tarefas/new` | Deep-link fullscreen fallback (direct URL/refresh), mirrors `RiskFormPage`. On done → `router.push('/opportunities/[id]/tarefas')` (**not** the opportunity detail — the natural "back" from a task form is the Tarefas list). |
| `/opportunities/[id]/tarefas/[taskId]/new` | Deep-link fullscreen fallback — create subtask of `[taskId]`. |
| `/opportunities/[id]/tarefas/[taskId]/edit` | Deep-link fullscreen fallback — edit. |

**Dialog close behavior (deviation from `RiskFormDialog`):** `RiskFormDialog.close()` does
`router.replace(pathname)`, dropping all params. On the Tarefas page this would also drop
`?view=`, silently switching the user back to Lista. **Decision:** `TaskFormDialog.close()` must
build from the current `URLSearchParams`, deleting only `tarefa`/`parent` and preserving `view`
(and any future params) — e.g. `router.replace(qs ? `${pathname}?${qs}` : pathname)`.

**Entry point (opportunity detail):** a new card directly below `AssigneesPanel`, same container
style (`bg-wh border border-bdr rounded-xl shadow-sm px-4 py-3 flex items-center justify-between`):
left side "🗂️ Plano de Atividades" + task count (e.g. "12 tarefas"); right side "Ver tarefas →"
button navigating to `/opportunities/${id}/tarefas`. Not a `TabsNav` tab — `TabsNav.onChange`
swaps content in place without navigating, which would be the wrong abstraction for a route change
(confirmed in RESEARCH Pattern 6).

### View switcher

Reuse `toolbar.tsx`'s segmented-control pattern verbatim: `bg-bg border border-bdr rounded-lg p-0.5`
wrapper, each option `px-2.5 py-1.5 rounded-md text-[12px] font-semibold`, active =
`bg-wh text-txt shadow-sm`, inactive = `text-mut hover:text-txt`. Labels hidden below `lg` breakpoint
(`hidden lg:inline`, icon-only on narrow viewports) — identical to the existing opportunities
switcher, so the same responsive behavior is inherited for free.

```
{ id: 'lista',  icon: '☰',  label: 'Lista'  }
{ id: 'kanban', icon: '📊', label: 'Kanban' }
{ id: 'gantt',  icon: '📅', label: 'Gantt'  }
```

### Responsive behavior (explicit risk area)

The page body (`<div className="px-6 lg:px-8 py-6"><div className="max-w-screen-2xl mx-auto">`,
mirrors `/opportunities/[id]/page.tsx`) **never** scrolls horizontally. Each wide view owns its
own horizontal scroll container, exactly like the two existing precedents already do:

- **Kanban:** `<div className="overflow-x-auto pb-3"><div className="flex gap-3 min-w-max ...">`
  — verbatim from `KanbanBoard`. On narrow viewports the board scrolls horizontally *within this
  div*; it is never hidden or replaced with a "view unavailable" message.
- **Gantt:** `<div className="overflow-x-auto"><div className="min-w-[760px] ...">` — verbatim
  from `GanttChart`. Same containment rule.
- **Lista:** table wrapped in its own `overflow-x-auto` (mirrors `RiskTable`), independent of the
  page scroll.

**Decision:** do not build a "Gantt/Kanban unavailable on mobile" fallback. The project's existing
Kanban/Gantt for opportunities already ship this exact graceful-horizontal-scroll pattern in
production with no narrower-viewport special case — inventing a new "unavailable" state here would
be inconsistent with the established precedent for the identical layout problem.

### Lista — row contract

Columns: `chevron` (only rendered if the row has ≥1 subtask — never a disabled/greyed button) |
`ID` (T001 / T001.1) | `Título` | `Responsável` | `Status` (icon+label pill) | `Início → Fim` |
`% Concluído` | `Ações` (✏️ editar, + subtarefa, 🗑️ excluir).

- **Parent row, has subtasks:** `Início → Fim` shows the **aggregated** span
  (`computeTaskRollup`'s `spanStart`/`spanDue`), not its own manual dates, prefixed with a small
  "Σ" glyph + `title="Datas agregadas das subtarefas"` tooltip so the computed nature is
  discoverable. `% Concluído` shows the rollup badge.
- **Parent row, zero subtasks:** shows its **own** `start_date`/`due_date` and a "—" in
  `% Concluído` (A3 — no rollup attempted for a task with nothing to aggregate).
- **Subtask row:** indented (`pl-8`), lighter title weight (`font-medium` not `font-bold`),
  own `start_date`/`due_date`/status; `% Concluído` column is "—" (not applicable to a leaf row).
- Expand/collapse: `useState<Set<string>>` local to the Lista component (independent from Gantt's
  own state — D-13). Chevron is a real `<button aria-expanded={expanded} aria-label="Expandir
  subtarefas de {título}" / "Comprimir subtarefas de {título}">`.
- Missing dates render "—" per-field independently (not "Sem data definida" — that phrase is
  reserved for the Gantt bar-less row, see below); this matches the project-wide "—" convention
  for any null scalar.

### Kanban — card and column contract

**Decision — Kanban is flat, not nested.** Every task and subtask (root or child) gets its own
independent card in the column matching its **own** persisted `status`. Kanban does **not**
implement expand/collapse (D-13/RESEARCH scope only requires expand/collapse for Lista/Gantt;
TASK-08 does not ask for hierarchy visualization in Kanban). Hierarchy is preserved as a
**caption only**, not an interaction:
- Parent card with ≥1 subtask: caption "🧩 {N} subtarefa(s)" (informational, non-interactive —
  no aggregated % is duplicated here; that's Lista/Gantt's job per D-02).
- Subtask card: caption "↳ subtarefa de {parent título}".

**Column:** `bg-bg border border-bdr rounded-xl w-[220px] flex-shrink-0` (verbatim width/shape from
`KanbanColumn`), header = icon + `TASK_STATUS_META` label (colored) + count pill only — **no**
secondary metric line (opportunities' Kanban shows "⏱️ Nh FTE/mês"; tasks have no equivalent
aggregate, so this line is simply omitted, not replaced with a placeholder).

**Card** (`bg-wh border border-bdr rounded-lg p-2.5 hover:border-pril hover:shadow-md`, verbatim
from `KanbanCard`), top to bottom:
1. Header row: `#T001` (bold, `text-pri`, `text-[10px]`) + hierarchy caption inline if applicable.
2. Title: `font-semibold text-[11px] line-clamp-2`.
3. **Blocked-reason box** (only when `status === 'bloqueio'`): `bg-red-50 dark:bg-red-950/40
   border border-red-200 dark:border-red-800 text-red-800 dark:text-red-300 rounded px-2 py-1
   text-[10px] line-clamp-2`, prefixed "🚫", `title=` full reason — satisfies "o motivo aparece
   no card" literally.
4. Footer row (`border-t border-slate-100 dark:border-slate-800`): assignee chip (avatar
   `w-5 h-5 rounded-full bg-pri text-white text-[9px] font-bold` initials + truncated name, or
   "Sem responsável" muted if `assignee_id` is null) on the left; due-date pill "📅 dd/mm" on the
   right, **omitted entirely** if `due_date` is null (unlike Lista/Gantt, the card does not show a
   "Sem data" placeholder — keeps the card uncluttered; the date's absence is simply not
   mentioned).

**Blocking-reason interception (D-03/TASK-09):** exact state machine from RESEARCH Pattern 5 —
do **not** optimistically move the card into Bloqueio until the reason is confirmed. `onDragEnd`
targeting `bloqueio` sets `pendingBlock` and returns without touching `tasks` state; the card
visually stays put (dnd-kit resets its own transform on drop) until `BlockedReasonDialog` confirms
or cancels. `BlockedReasonDialog` mirrors `RiskFormDialog`/`DeleteRiskButton` structurally: overlay
`z-[60]`, ESC/click-outside = cancel, confirm button disabled while textarea is empty. Moving a
card **out** of `bloqueio` to any other status always sends `blocked_reason: null` explicitly in
the Server Action payload (Pitfall 4 — never omit the field).

### Gantt — row contract

Adapts `components/opportunities/gantt/GanttChart.tsx` (not `proposal/GanttChart.tsx` — see
RESEARCH Pattern 4), same `leftPct`/`widthPct` technique, same 6-tick `dd/mm/aa` axis, same "today"
red line, same hachured `ongoing` treatment. Row label column width mirrors the existing 240px
(`w-[240px] shrink-0`), min container width `min-w-[760px]`.

- **Domain `t0`/`t1`:** computed once over **every** task/subtask that has **both** `start_date`
  and `due_date` set, regardless of current expand/collapse state (Pitfall 3 — expanding a row
  must never shift other bars).
- **Parent row, has subtasks:** bar spans `computeTaskRollup`'s `spanStart`→`spanDue`. Rendered as
  a two-layer bar (mirrors `proposal/GanttChart.tsx`'s base+overlay trick): a lighter/neutral base
  bar for the full span, with a solid accent-colored progress overlay whose width = `percentComplete%`.
- **Parent row, zero subtasks:** bar uses its own `start_date`/`due_date`, colored by its own
  `TASK_STATUS_META.color` — rendered exactly like a normal single-status bar, no overlay (A3).
- **Subtask row:** rendered indented immediately below its expanded parent, bar colored by its
  **own** `TASK_STATUS_META.color`.
- **Task missing either date (parent or subtask):** row still renders (label, assignee, status),
  but shows the text **"Sem data definida"** in place of the bar; this task does **not** contribute
  to the `t0`/`t1` domain calculation (A4).
- Expand/collapse: separate `useState<Set<string>>` local to the Gantt component (independent from
  Lista's — D-13), same chevron accessibility contract (`aria-expanded`, `aria-label`).

### Accessibility (explicit risk area)

- **Expand/collapse:** always a real `<button>` with `aria-expanded` + a descriptive
  `aria-label` naming the task title (never an icon-only unlabeled div-with-onClick). Focus-visible
  ring matches the existing input/link focus treatment (`focus:ring-1 focus:ring-pri`, project's
  established focus style — nothing new to invent).
- **Kanban drag-and-drop keyboard path — decision:** do not rely solely on `@dnd-kit`'s
  `KeyboardSensor` (the existing `Board.tsx` only wires `PointerSensor`, and dnd-kit's keyboard
  mode requires custom collision/announcement wiring this repo has never built). **Every Kanban
  card additionally exposes a keyboard-operable status control** — a small `<select>` or a
  "Mover para ▾" button revealing the 4 statuses — reachable by Tab + Enter/Space, that calls the
  **same** `updateTaskStatus` action (and triggers the same blocked-reason dialog when the target
  is `bloqueio`). This guarantees full keyboard operability without needing dnd-kit's more complex
  keyboard-sensor + custom drag-announcement machinery, and is simpler to implement and test.
- **Color-independence of status (explicit requirement):** every status rendering — column header,
  card pill, Lista badge — pairs the `TASK_STATUS_META.color` with its `icon` **and** `label` text.
  No status is ever conveyed by a bare colored dot with no text/icon (unlike the small red
  "criticidade" dot on opportunity Kanban cards, which is decorative/secondary — task status is the
  *primary* signal of the whole view and must never rely on color alone).
